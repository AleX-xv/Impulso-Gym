CI y despliegue de Impulso Gym

Práctica integradora · ULEAM · 26 de noviembre de 2026

Introducción y arquitectura

Impulso Gym permite consultar rutinas, marcar ejercicios y registrar minutos de entrenamiento. La práctica incorpora pruebas automatizadas a un proyecto que ya se publicaba en Azure desde GitHub.

Alcance de la práctica

La entrega comprueba la carga del panel, una ruta inexistente y la sonda de disponibilidad. En Azure se verificó el recorrido de una rutina con datos de demostración. En la rama de práctica se reprodujo un fallo HTTP y se corrigió antes de generar el paquete 1.1.0.

Flujo de entrega

Workspace o VS Code → rama de GitHub → validación de Actions → revisión por PR. En el esquema existente, un push a main activa el workflow de Azure y el App Service sirve el sitio al navegador.

Pipeline y reproducibilidad

El workflow practica-ci.yml se ejecuta en push, en PR hacia main y admite ejecución manual. La tarea se detiene al fallar un paso obligatorio.

Fallo controlado y corrección

Se introdujo deliberadamente un estado HTTP 500 en /healthz dentro de practica/ci-cd. El criterio CA-03 pedía 200 y el cuerpo OK para confirmar que el servidor podía atender solicitudes.

EjecuciónResultado observado
GitHub Actions n.º 1Fallo en Ejecutar pruebas HTTP. CA-01 y CA-02 pasan. CA-03 recibe 500 frente a 200. El proceso sale con código 1 y el empaquetado queda omitido.
GitHub Actions n.º 2Se cambia el estado de 500 a 200. Las tres pruebas pasan en el código y en release/. Se publica un artefacto vinculado al commit 4ed6d9d.
GitHub Actions n.º 3La apertura del PR vuelve a lanzar el workflow, con el mismo conjunto de pruebas y empaquetado.

Extracto del registro fallido

CA-01  Panel y recursos públicos                 pasa
CA-02  Ruta inexistente devuelve 404             pasa
CA-03  Disponibilidad de /healthz                falla
       500 !== 200. Exit code 1.

Análisis del fallo

El cuerpo respondía OK, pero el estado HTTP indicaba error del servidor. Una sonda que comprueba el código HTTP interpretaría el servicio como indisponible. La corrección cambia la respuesta a 200 y conserva la prueba original para detectar futuras regresiones.

El fallo y su corrección se ejecutaron en la rama de práctica. El workflow de despliegue histórico de Azure se dispara en main.

Despliegue y pruebas del producto

El sitio de Impulso Gym responde en Azure. Actions registró el último despliegue exitoso observado para ese App Service el 28 de octubre de 2026, en el commit e95711e y la versión 1.0.0. La práctica generó la versión 1.1.0 en su rama.

VerificaciónResultado observado el 26 de noviembre de 2026
Principal en AzureMi panel → Pausa y movilidad → marcar cinco ejercicios → ingresar 17 minutos → Registrar entrenamiento. El panel mostró 17 min. En Mi actividad quedó Pausa y movilidad · 17 min · Movilidad y el registro persistió al recargar. Se eliminó el dato de prueba al terminar.

Recuperación revisión y aportes

Recuperación a una versión estable

Si un cambio en producción causa una regresión, consulta Actions y el Centro de implementación para identificar la versión estable. Crea una rama desde main, revierte el cambio causante con git revert, abre un PR y comprueba las pruebas. Al integrar, verifica el nuevo despliegue en Azure y repite el recorrido principal y el 404. El último punto estable registrado para Azure es e95711e (1.0.0).

git worktree add --detach ../impulso-estable e95711e
cd ../impulso-estable
npm ci --no-audit --no-fund
npm start

El comando abre una copia local de la versión estable sin mover la rama actual. Usa el mismo origen para consultar el historial del navegador. El código publicado y los datos de localStorage tienen ciclos distintos.

Secretos del entorno

El despliegue existente referencia secretos de GitHub para iniciar sesión en Azure mediante OpenID Connect. El job de despliegue pide el token de identidad y el job de CI solo lee el repositorio. El paquete de práctica incluye una lista de archivos de ejecución y las pruebas funcionan sin credenciales. La configuración privada permanece fuera del repositorio, de los registros incluidos y del PDF.

Trazabilidad y revisión

HG-01 vincula el acceso al panel y las rutas inexistentes con CA-01 y CA-02. OP-01 vincula el monitoreo de disponibilidad con CA-03. El PR #1 contiene los criterios, el enlace rojo y una guía de revisión. La aprobación del compañero queda pendiente de registro en GitHub.
